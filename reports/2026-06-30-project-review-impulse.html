Whole-project code review · impulse effort

Every store gets written before the ledger agrees it happened. That's the pattern behind most of this.

This is a whole-project audit of invoice.py, zd.py, the shell wrappers, and the git pre-commit PII guard — not a diff review. It read every source file in the repository (5 files, grouped into 3 clusters) and surfaced 103 verified findings, of which 72 survived a second adversarial pass. This report features the 25 most severe, all correctness bugs, ranked by the cluster they belong to; the remaining 47 (cleanup, conventions, documentation, testing) are in the collapsed full inventory in Chapter 5 so nothing is hidden.

The dominant pattern: PDFs, the CSV ledger, and the SQLite database are three independent stores with no shared transaction. Writes land on disk in a fixed order with no rollback, so a duplicate invoice number, a failed DB update, or a locked file mid-operation leaves the three stores disagreeing — sometimes invisibly, sometimes as a raw crash, once as outright double-billing.

Chapter 1Setup & methodology

Informational · establishes scope and trust in the method · no action required

What this is about

invoice.py and zd.py together form a solo-consultant billing tool: invoice.py generates PDF invoices and maintains a flat CSV ledger; zd.py sits on top of it with a SQLite database of time-tracking sessions and expenses, and drives invoice.py's own functions to actually produce invoices. Two shell wrappers (invoice-wrapper, zd-wrapper) resolve symlinks and activate a venv before dispatching to the Python entry points. A git pre-commit hook (hooks/pre-commit) scans staged diffs for PII before allowing a commit.

This review reads the whole project, not a diff — every source file was in scope: invoice.py, zd.py, invoice-wrapper, zd-wrapper, and hooks/pre-commit. It ran at the impulse effort tier: fast, single-pass, but every candidate finding was individually verified against the actual source before being reported — nothing here is a guess.

What we ran

The review followed a five-stage pipeline. Each stage's job: 

1. MAP        — partition the 5 files into clusters by shared root cause / area
2. FIND       — dispatch finders per cluster to read source and propose candidate findings
3. VERIFY     — re-check each candidate against the actual file:line; reproduce where practical
4. SWEEP      — a second pass looking for anything the first pass missed
5. SYNTHESIZE — dedupe root causes, rank by severity, write this report

28 finders proposed 110 candidate findings across the 5 files. Verification confirmed or downgraded each one against the live source — reproducing failure modes directly where feasible (e.g. actually staging a PII-shaped diff line and running the hook's grep, actually driving group_sessions_by_week with fractional hours to compare confirmation-total vs. saved-total). 103 candidates were verified as real findings (CONFIRMED or PLAUSIBLE); 7 were refuted outright after re-reading the code — those are listed in Chapter 5 so the audit trail is visible. After deduplicating findings that share one root cause across multiple call sites, 72 distinct findings remain in the full inventory; this report features the 25 most severe.

Chapter 2Cluster A — non-transactional multi-store writes

Blocking · 5 findings, all CONFIRMED · PDF + CSV + SQLite disagree with no rollback

What this is about

Every invoice touches three independent, un-transacted stores: the PDF file on disk, invoice.py's CSV ledger, and (when driven via zd) the zd SQLite database. Each store is written with its own atomicity guarantee — the PDF write is a plain file write, the CSV write uses a file lock + atomic replace, the DB write uses a SQLite transaction — but nothing wraps all three together. The write order is fixed (PDF, then CSV, then DB) and nothing rolls back an earlier store when a later one fails.

This is the single highest-leverage cluster in the review: one architectural gap (no shared transaction / no PDF-write deferred until after validation) produces five distinct, independently-reproducible failure modes, including actual double-billing.

What we found

invoice.py:1185 CONFIRMED

cmd_new writes the PDF via generate_pdf() before save_to_csv() validates the invoice number is unique, so a duplicate number silently overwrites an existing invoice's PDF file on disk before the duplicate-check exception aborts the ledger write. [same root cause also at: /Users/dave/Documents/Projects/invoice/invoice.py:1185, invoice.py:999, /Users/dave/Documents/Projects/invoice/zd.py:1284]

Failure scenario

User re-enters (or defaults to) an invoice number that already exists in the ledger. generate_pdf() (line 946, pdf.output()) writes/overwrites the PDF at the computed path with the new content/total; save_to_csv() then raises ClickException('...already exists...') and the CLI exits. Verified via direct reproduction: the original PDF (e.g. $100.00 total) is silently replaced on disk with the new content (e.g. $10,000.00), while the CSV ledger still shows the old $100.00 row pointing at that now-mismatched PDF file -- permanent, silent loss of the original invoice PDF with no warning that a file was overwritten.

zd.py:1290 CONFIRMED

In cmd_invoice's new-invoice path, `inv_mod.generate_pdf(...)` (zd.py:1274) and `inv_mod.save_to_csv(...)` (zd.py:1284) durably write the PDF and append a 'Sent' row to invoice.py's CSV ledger — both using invoice.py's own file-lock/atomic-write machinery, fully committed to disk — BEFORE the zd SQLite work (`INSERT INTO invoices` at zd.py:1290-1294, then `UPDATE sessions ... SET invoice_id` and `UPDATE expenses ... SET invoice_id` at zd.py:1309-1310) runs inside the same `with get_conn() as conn:` block opened at zd.py:1055. None of lines 1266-1310 are wrapped in try/except, and sqlite3.Connection's context-manager `__exit__` only commits-or-rolls-back (it never partially commits). If any exception occurs between the successful save_to_csv() call and the completion of the two UPDATE statements (a DB constraint error, KeyboardInterrupt, disk-full on the DB, etc.), the CSV ledger and PDF are left as a fully realized 'Sent' invoice with no corresponding row in the zd `invoices` table, and the underlying sessions/expenses remain `invoice_id IS NULL` (unbilled) in the zd DB. This is the inverse-and-worse case of the already-flagged 'zd.py:1284 save_to_csv exception not caught' finding: here save_to_csv *succeeds*, so the external ledger is durably correct while the internal DB silently reverts, with no rollback of the PDF/CSV side.

Failure scenario

zd invoice acme generates and durably saves the PDF + CSV row for invoice 2026-0007, then the DB INSERT/UPDATE step fails or the process is killed (e.g. Ctrl-C, disk pressure, DB lock timeout) before the sessions are marked billed. The same unbilled sessions are still selectable by `zd invoice acme` on the next run: the user re-runs it, a *new* invoice number (2026-0008) is generated for the identical sessions, and the client is billed twice for the same work under two different invoice numbers. The orphaned 2026-0007 CSV/PDF entry has no zd DB record, so `zd paid 2026-0007` fails with 'not found in zd database' even though a real PDF and CSV row exist for it — a ledger the operator has no built-in command to reconcile.

zd.py:1173 CONFIRMED

Unguarded Path(old_path).unlink() in the --regenerate flow, inside the get_conn() transaction, can crash and roll back a DB update that the CSV ledger update (already durably written) does not roll back

Failure scenario

In `zd invoice <client> --regenerate <num>`, after the new PDF is generated and the CSV ledger row is atomically updated (zd.py:1146-1168, all inside `with get_conn() as conn:` starting at line 1055), the old PDF is deleted with a bare `Path(old_path).unlink()` (line 1173) -- no try/except. If that delete fails (permission denied, file held open in Preview/Finder, read-only/network mount), the exception propagates out of the `with get_conn()` block. Because sqlite3's connection context manager rolls back the pending transaction on any exception (and never explicitly commits until clean exit), the just-executed `UPDATE invoices SET total = ?, pdf_path = ?` (line 1146-1149) is rolled back. But the CSV ledger write a few lines earlier used its own file lock + atomic write (`inv_mod._atomic_write_csv`) and already landed on disk, outside the SQL transaction. Result: the CSV ledger now shows the new total/pdf_path for that invoice while the zd SQLite DB still has the old ones -- a permanent cross-ledger desync -- and the CLI exits via an unhandled traceback instead of a clean error, with both the old and new PDF left on disk.

zd.py:1146 CONFIRMED

`zd invoice --regenerate` recomputes the total from the client's CURRENT rate (live `cl.rate` join at line 1090/1117), then overwrites the stored total and PDF of an already-sent/paid invoice. [same root cause also at: /Users/dave/Documents/Projects/invoice/zd.py:1090]

Failure scenario

A consultant changes a client's hourly rate, then later runs `zd invoice <client> --regenerate <old-invoice-number>` to fix a cosmetic PDF issue on a previously sent (possibly already-paid) invoice. The regenerated PDF and the `invoices.total` DB row silently reflect the new rate rather than what the client was actually billed, corrupting the historical financial record with no warning that the rate differs from the original.

zd.py:892 CONFIRMED

`zd edit --force` (and `zd edit-expense --force`) allow changing hours/date/notes on an already-billed session without touching the parent `invoices.total`, so the DB/CSV total silently drifts from the sum of its line items until the user remembers to `--regenerate`.

Failure scenario

After `zd edit 14 --hours 3.0 --force` on a session already attached to invoice `2026-0002`, `zd status` and `zd sessions --all` keep showing the invoice's old `invoices.total` (and the CSV ledger keeps the old `total` too), while the underlying session hours have changed — the PDF that was already emailed to the client also still reflects the old figure. Nothing warns the user that the invoice is now inconsistent with its sessions, so they may collect/report the stale total unless they separately remember to run `zd invoice <client> --regenerate <num>`.

The throughline: PDFs and CSV rows are durably written to disk before the operation that's supposed to validate or finalize them completes. invoice.py:1185 and zd.py:1290 are the sharpest examples — one silently overwrites a PDF before a duplicate-number check fires, the other leaves a fully "Sent" invoice with no corresponding zd DB row if the DB write fails after the CSV succeeds, which reproduces as literal double-billing on retry. zd.py:1173 and zd.py:1146 show the same pattern in the regenerate path: an unguarded file delete can roll back a DB transaction that the already-flushed CSV write does not roll back, and regeneration silently re-prices a historical invoice at the client's current rate. zd.py:892 is the softer end of the same family — editing a billed session doesn't touch the invoice total it belongs to, so the three stores drift apart by omission rather than by crash.

Where this leaves us

AReorder writes and wrap DB + CSV in one recoverable unit

Validate the invoice number is unique and the DB write will succeed before generating the PDF, not after. For the zd new-invoice path, either move the CSV/PDF write after the DB `INSERT`/`UPDATE`s succeed, or add a reconciliation step that can detect and repair a CSV/PDF row with no matching DB row (and vice versa). Wrap the regenerate flow's file delete in a try/except that doesn't propagate into the DB transaction's rollback path.

What's lost: more code, and a real transactional design decision (which store is the source of truth) has to be made explicitly. What's gained: the double-billing and cross-ledger desync failure modes become structurally impossible instead of relying on nothing going wrong.

BAdd a reconciliation command, leave write order as-is

Ship a zd reconcile command that diffs the CSV ledger against the zd DB and flags/fixes orphaned rows on either side. Cheaper than Path A, but treats the symptom (desync recovery) rather than the cause (desync happening at all), and does nothing for the silent PDF-overwrite case (invoice.py:1185) since there's no "orphan" to detect there — the old PDF is just gone.

What's lost: the underlying race/ordering bug remains; a user has to remember to run reconcile. What's gained: fast to ship, and provides real value even after Path A is eventually done (belt-and-suspenders for a solo-operator tool).

CLeave as-is; document the risk

Add a README/HISTORY note describing the desync risk and rely on manual vigilance (the "Cross-ledger desync" and "double-billing" scenarios are rare in practice for a low-volume solo consultant).

Declined: the double-billing scenario (zd.py:1290) and the silent-overwrite scenario (invoice.py:1185) are both financial-record-corrupting and were reproduced directly, not hypothesized — documentation doesn't prevent either.

Recommended action

Fix the write ordering. Pick Path A, starting with invoice.py:1185 (duplicate-number check before PDF write) and zd.py:1290 (DB write before/atomic-with CSV finalize) — those two are the ones with directly reproduced financial-record damage.

Every other correctness bug in this report is a bounded, single-command failure. This cluster is the one where the same root cause produces silent data loss (an overwritten PDF, an orphaned invoice) and a path to double-billing a client — the two outcomes a solo consultant's billing tool exists to prevent.

Escalate to: n/a — Dave-decidable. This is a design decision about write ordering, not a call that needs another stakeholder.

Chapter 3Cluster B — other high-impact correctness bugs

Action needed · 13 findings, all CONFIRMED · independent bugs, no shared root cause

What this is about

Unlike Cluster A, these 13 findings don't share one root cause — each is an independent correctness bug in either invoice.py or zd.py, found by reading the actual code paths for CSV parsing, config loading, rate/hours math, and client matching. They range from unhandled crashes on legacy or corrupted files, to silent financial-total mismatches, to a config-sync path that bypasses the project's own safe-write machinery.

What we found

zd.py:624 CONFIRMED

cmd_log only validates hours <= 0, not finiteness; float('inf') passes and Decimal quantize on it raises after the row is already committed [same root cause also at: /Users/dave/Documents/Projects/invoice/zd.py:624]

Failure scenario

`zd log acme inf "notes"` (or a typo/paste that yields `inf`) passes the `hours <= 0` guard (inf <= 0 is False), so the INSERT at zd.py:629-632 runs inside `with get_conn()` and commits cleanly. The very next line, `amount = to_money(hours * c["rate"])` at zd.py:634, does `Decimal(str(float('inf'))).quantize(...)`, which raises `decimal.InvalidOperation` uncaught -- the command crashes with a raw traceback. Worse, the garbage 'Infinity' hours row is now permanently stored in ~/.zd.db. Every subsequent `zd status`, `zd sessions`, or `zd invoice <client>` for that client sums hours (including the inf row) and calls `to_money()` on the total, hitting the same InvalidOperation and crashing -- the tool becomes unusable for that client until someone manually deletes the row from the SQLite DB (e.g. via `sqlite3 ~/.zd.db`). Note `hours=nan` is worse silently: `nan <= 0` is also False so it passes validation, but sqlite3 stores Python NaN as NULL, and `to_money(nan * rate)` returns `Decimal('NaN')` without raising, so a bogus session with silently-nulled hours gets logged with no error at all.

zd.py:493 CONFIRMED

group_sessions_by_week() rounds each week's hours with float round() before pricing that week, while the pre-generation confirmation total (lines 1253-1256/1117) prices the unrounded aggregate hours in one shot — the two totals can diverge. [same root cause also at: /Users/dave/Documents/Projects/invoice/zd.py:494]

Failure scenario

Verified numerically: sessions summing to 2.015 raw hours split across two weeks (2.01h + 0.005h) yield a click.confirm 'Proceed?' total of $302.25 (to_money(total_hours*rate)) but an actual generated/saved invoice total of $303.00 (sum of independently per-week-rounded amounts) at $150/hr — a $0.75 mismatch between the dollar figure the user approves and what actually lands in the PDF, CSV ledger, and DB.

zd.py:1062 CONFIRMED

Client-profile matching in cmd_invoice uses bidirectional substring containment on names, so one client's name being a substring of another can silently pick the wrong invoice.py profile. [same root cause also at: /Users/dave/Documents/Projects/invoice/zd.py:1061]

Failure scenario

If ~/.invoice_config.json has two clients where one name contains the other (e.g. 'Smith Consulting' and 'Smith Consulting East'), `zd invoice smith` matches whichever profile appears first in the config list purely by substring containment. The generated PDF's Bill-To address/contact can be for the wrong client, so one client's invoice gets mailed with another client's billing details.

zd.py:1066 CONFIRMED

zd.py's `cmd_invoice` never checks for an empty invoice.py `clients` list, unlike invoice.py's own `cmd_new` guard

Failure scenario

`invoice.py`'s `cmd_new` explicitly aborts with "No client profiles found..." when `config['clients']` is empty (invoice.py:1147-1150) before calling `generate_pdf`/`save_to_csv`. zd.py's `cmd_invoice` (zd.py:1059-1072) only prompts the user to pick a client profile `if not matched_client and inv_clients:` — if `inv_clients` (i.e. `config.get('clients', [])`) is itself empty, that guard is falsy and `matched_client` stays `None`. It is then passed straight into `inv_mod.generate_pdf(..., client=matched_client, ...)` (zd.py:1140-1143 / 1274-1277) and `inv_mod.save_to_csv(..., client=matched_client, ...)` (zd.py:1284-1287). Inside those, `client is None` falls back to `config['clients'][0]` which also doesn't exist, so both silently fall back to `{}` (invoice.py:765-767, 970-972). The result: `zd invoice <client>` happily generates and finalizes a real PDF invoice with a blank "Bill To" section and an empty `payer_name` in the CSV ledger, marks the sessions as billed in the DB, and gives no warning — instead of failing loudly like the equivalent invoice.py CLI path does.

invoice.py:1246 CONFIRMED

cmd_status assigns a 'status' key to the row dict and writes back using the CSV file's original fieldnames without checking whether 'status' is actually one of them, unlike save_to_csv which explicitly guards against this same legacy-header case.

Failure scenario

Running `invoice.py status <num> Sent` against a ledger CSV that predates the status column (confirmed by HISTORY.md as a real prior format) adds a 'status' key to the row dict via the `_csv_field_key(...) or 'status'` fallback, then calls _atomic_write_csv(path, rows, file_headers) with the original (status-less) file_headers. csv.DictWriter defaults to extrasaction='raise', so writerows() raises ValueError('dict contains fields not in fieldnames'), crashing the status-update command and leaving the user unable to update invoice status on older ledgers -- reproduced directly.

invoice.py:708 CONFIRMED

_multi_cell_height() raises IndexError when a line-item description is non-empty but consists solely of whitespace, because str.split() on an all-whitespace string returns an empty list before words[0] is accessed.

Failure scenario

User enters a line-item description that is just spaces (e.g. accidentally hits the space bar then Enter) -- passes cmd_new's `if not description` blank-check since the string is non-empty. All line items are collected interactively, then generate_pdf() calls _multi_cell_height() on that description, which does `words = text.split()` (yields []) then `current = words[0]`, raising an uncaught IndexError that crashes the program after the user has finished entering all line items -- none of the entered data is saved since generate_pdf() runs before save_to_csv().

invoice.py:506 CONFIRMED

_run_config_setup accesses config["payee"]["name"] directly instead of using setdefault, unlike every other top-level config section (clients, invoice_header, payment, storage) which are defensively back-filled in both load_config() and _run_config_setup(). [same root cause also at: /Users/dave/Documents/Projects/invoice/invoice.py:1203, /Users/dave/Documents/Projects/invoice/invoice.py:472]

Failure scenario

If ~/.invoice_config.json is missing the top-level 'payee' key (e.g. a hand-edited or partially-migrated config), running `invoice.py config` calls _run_config_setup(existing) which does config = deepcopy(existing) (not merged with DEFAULT_CONFIG) and then immediately raises KeyError('payee') at config["payee"]["name"] -- crashing the exact command a user would run to repair a broken config, with no recovery path short of manually editing the JSON file.

invoice.py:621 CONFIRMED

get_next_invoice_number's row-parsing loop only catches (ValueError, KeyError), but a short/legacy-format CSV row can yield None for the invoice_number field, causing an uncaught TypeError.

Failure scenario

csv.DictReader fills missing trailing columns with None (restval default). The code explicitly supports legacy ledgers whose invoice_number column is not first (_csv_field_key's docstring cites 'Invoice Number' vs 'invoice_number' header remapping). If such a legacy-ordered ledger contains any short/malformed row (e.g. a hand-edited or partially-copied line with trailing columns dropped), row.get(inv_key, '') returns None, and `if "-" in invoice_str:` raises `TypeError: argument of type 'NoneType' is not a container or iterable`. This TypeError is not one of the (ValueError, KeyError) caught at line 627, so it propagates as an unhandled traceback and crashes `invoice.py new` (and any other command that first computes the next invoice number) instead of the friendly click.ClickException style used elsewhere in the file. Verified interactively: DictReader on a 2-column-header, 1-column-data row produces invoice_number=None and the `in` check raises TypeError.

invoice.py:431 CONFIRMED

load_config() only catches JSONDecodeError/OSError around json.load, but a syntactically-valid JSON file whose top level isn't an object (e.g. `[]`, `null`, a bare string) crashes with an unhandled AttributeError on the very next line.

Failure scenario

If ~/.invoice_config.json is ever truncated/corrupted into something that is still valid JSON but not a dict (e.g. an interrupted write leaves `null` or an empty array, or a user manually pastes a JSON array), `json.load` succeeds and returns a non-dict; the immediately following `if "payer" in cfg and "clients" not in cfg:` / `cfg.setdefault(...)` calls raise `AttributeError: 'list' object has no attribute 'setdefault'` (or 'argument of type NoneType is not iterable' for `null`). This bypasses the intended `click.ClickException(f"Config file ... is not valid JSON")` friendly-error path entirely and every single CLI command crashes with a raw traceback instead of guiding the user to re-run `invoice.py config`. Verified interactively: `json.loads('[]').setdefault(...)` raises AttributeError.

invoice.py:250 CONFIRMED

_read_csv_with_headers opens the ledger with a fixed 'utf-8-sig' encoding and no error handling; a non-UTF-8 or corrupted ledger file raises an unhandled UnicodeDecodeError everywhere it's called.

Failure scenario

Every ledger read path (get_next_invoice_number, _resolve_invoice_pdf_path, save_to_csv's duplicate check, cmd_status, cmd_list) funnels through _read_csv_with_headers with no try/except for decoding or csv parsing errors. If the CSV ledger is ever saved/edited with a non-UTF-8 encoding (e.g. opened and re-saved in Excel with a different codepage, or a stray corrupted byte from a copy/paste), `list(reader)` raises UnicodeDecodeError with a raw Python traceback, crashing `invoice new`, `invoice list`, `invoice status`, and `--invoice`/`--ledger` shortcuts alike — including blocking invoice creation entirely until the user manually fixes ledger encoding, with none of the friendly click.ClickException messaging used for the equivalent JSON-config parse-error path in load_config().

zd.py:206 CONFIRMED

_sync_client_to_config() reads/writes ~/.invoice_config.json directly instead of going through invoice.py's load_config()/save_config() contract [same root cause also at: /Users/dave/Documents/Projects/invoice/zd.py:230]

Failure scenario

`zd client add <name> ...` (which calls `_sync_client_to_config`, zd.py:206-231) reads the config with raw `json.loads` and writes it back with `CONFIG_FILE.write_text(json.dumps(...))`, bypassing invoice.py's `load_config()` migration logic and `save_config()`/`_atomic_write_json()` (invoice.py:224-245, 409-452). Two concrete consequences: (1) if the config still has invoice.py's legacy `"payer"` key (pre-migration), `_sync_client_to_config` does `config.setdefault("clients", [])` and appends to a *new* empty list, permanently orphaning the old `payer` data — the next `load_config()` call sees `"clients" in cfg` already true and never runs the `payer`→`clients` migration (invoice.py:431-432), so the legacy payee/client info is silently lost. (2) The write is non-atomic (`write_text` truncates in place, no tempfile+os.replace) and never chmods to 0o600 like `save_config` does, so a crash mid-write can corrupt the config (next `load_config()` raises `json.JSONDecodeError` → `click.ClickException`, breaking every subsequent `invoice.py`/`zd.py` invocation), and a config file created for the first time this way gets default (non-restrictive) permissions, exposing client PII in violation of the project's 0o600 convention.

zd.py:213 CONFIRMED

_sync_client_to_config swallows any config read/parse failure (not just missing file) and silently rebuilds+overwrites the live config with a near-empty stub

Failure scenario

`_sync_client_to_config` (called from `cmd_add_client` after every `zd add-client`) wraps `json.loads(CONFIG_FILE.read_text(...))` in a bare `except Exception: config = {}`. Any failure other than the file not existing -- a transient read error, an encoding hiccup, or a JSON file left mid-write/corrupted by a concurrent invoice.py process -- causes the entire config object (payee details, invoice.py client list, storage paths, weekly_summaries settings) to be replaced by an empty dict, into which only the single new client entry is inserted. `CONFIG_FILE.write_text(...)` at zd.py:231 then persists that stub over the real config. A `.bak` timestamped backup is made first (line 230), so recovery is possible, but the live `~/.invoice_config.json` used by both `zd` and `invoice.py` is destroyed on the next `zd add-client` call until the user notices and manually restores from a backup.

zd.py:1243 CONFIRMED

Next-invoice-number selection compares zero-padded numeric strings with Python's `max()`, which is only numerically correct while both candidates stay within the same fixed 4-digit width — it silently breaks once the sequence number would overflow that width.

Failure scenario

`db_next = f"{current_year}-{db_next_num:04d}"` (line 1243) and `csv_next` (from invoice.py) are compared with `invoice_number = max(csv_next, db_next)` (line 1246) as plain strings. Lexicographic ordering of zero-padded strings matches numeric ordering only up to 9999; once a year's invoice count reaches 10000, `db_next_num:04d` formats as '10000' (Python's `:04d` is a minimum width, not a hard cap) and the string '2026-10000' sorts lexicographically *before* '2026-9999' (comparing '1' < '9' at the first differing character), so `max()` would pick the smaller/older-looking string as 'next', risking a duplicate or out-of-order invoice number being assigned. Low likelihood for a solo consultant's invoice volume, but a real latent string-vs-numeric comparison bug in the invoice-numbering logic that both invoice.py and zd.py rely on for uniqueness.

Three sub-patterns worth naming. First, input validation gaps that reach persistence before they crash: zd.py:624 lets inf/nan hours get committed to the sessions DB before the arithmetic that would reject them runs, and zd.py:493 shows the pre-generation confirmation total and the actually-saved total can diverge by real money (verified: $302.25 approved vs. $303.00 saved) because rounding happens per-week before pricing instead of once at the end. Second, defensive coding that exists in one place but not its sibling: invoice.py:506, invoice.py:621, invoice.py:431, and invoice.py:250 are all cases where a nearby function has the right guard (setdefault, broader exception catching, dict-type check, encoding fallback) and this one doesn't. Third, zd.py's config-sync path re-implements what invoice.py already does safely: zd.py:206 and zd.py:213 bypass invoice.py's atomic-write and migration-aware load_config()/save_config() contract, risking silent data loss on the shared config file both tools depend on.

Where this leaves us

AFix in two batches: money-affecting first, then crash-hardening

Batch 1 (money-affecting, fix first): zd.py:624 (finite-hours validation), zd.py:493 (rounding-before-pricing), zd.py:1062/1066 (client-matching/empty-list), zd.py:1243 (invoice-number overflow). Batch 2 (crash-hardening on legacy/corrupt input): invoice.py:1246, :708, :506, :621, :431, :250, and zd.py:206/213 (route through invoice.py's existing safe-config helpers instead of reimplementing).

What's lost: thirteen separate small PRs/commits instead of one sweeping change. What's gained: each fix is independently testable and low-risk to review; nothing here requires a design decision the way Cluster A does.

BAdd a shared input-validation/config-loading layer first

Before fixing each site individually, extract a small shared validator (finite-number check, safe-JSON-load-returns-dict check) used by both files, then apply it everywhere at once. Reduces the chance of fixing one call site and missing a sibling with the identical gap.

What's lost: more upfront design work before any single bug is fixed. What's gained: lower chance of the same class of bug reappearing at a fourteenth call site next month.

Chapter 4Cluster C — security & process gaps

Action needed · 7 featured findings (pre-commit hook), all CONFIRMED · plus related security items from the full inventory

What this is about

This project's git pre-commit hook (hooks/pre-commit) is the safety net meant to enforce "no PII in the project" from the global CLAUDE.md hard rules. Seven distinct, independently-reproducible ways exist for a commit carrying real PII to pass that guard silently — no error, no warning the operator would notice by default. The full inventory (Chapter 5) also carries three related items worth naming here even though they weren't in the featured 25: plaintext banking secrets in the config file instead of Bitwarden Secrets Manager, missing file logging, and wrapper scripts that trust any active $VIRTUAL_ENV rather than specifically this project's venv.

What we found

hooks/pre-commit:28 CONFIRMED

`grep -E '^\+[^+]'` used to isolate added diff lines mis-fires on content that itself starts with a literal `+` [same root cause also at: /Users/dave/Documents/Projects/invoice/hooks/pre-commit:28]

Failure scenario

A staged line whose actual content begins with '+' (e.g. an E.164 phone number like "+15551234567", or code like "++x"/"+=") appears in the unified diff as "++15551234567" (diff's own '+' marker plus the content's leading '+'). The regex `^\+[^+]` requires the second character to be non-'+', so it treats this exactly like the `+++ b/file` header noise it's meant to skip and silently drops the line from `$added_lines`. It is therefore never checked against `hooks/pii-patterns.txt`, so PII that happens to start with '+' (a very common phone-number format) is committed without the guard ever seeing it. Verified empirically: staging a file containing an added line `+15551234567` and running `git diff --cached --no-color -U0 | grep -E '^\+[^+]'` returns only the other added line and silently omits the phone-number line.

hooks/pre-commit:22 CONFIRMED

`':(exclude)hooks/*'` exempts every file under `hooks/`, not just the pattern file itself, from PII scanning [same root cause also at: /Users/dave/Documents/Projects/invoice/hooks/pre-commit:22, /Users/dave/Documents/Projects/invoice/hooks/pre-commit:22, /Users/dave/Documents/Projects/invoice/hooks/pre-commit:22]

Failure scenario

The exclusion is scoped to the whole `hooks/` directory (to avoid self-tripping on the pattern file's own PII strings), but that means any other new file added under `hooks/` — e.g. a new helper script, a debug log accidentally saved there, or notes in a future `hooks/README.md` — can contain real PII/secrets and the pre-commit guard will never inspect it, since the exclude pathspec removes it from `$staged_diff` before the added-lines/pattern matching ever runs.

hooks/pre-commit:15 CONFIRMED

Missing `pii-patterns.txt` disables the PII guard with only a stderr warning, not a blocked commit [same root cause also at: /Users/dave/Documents/Projects/invoice/hooks/pre-commit:16, /Users/dave/Documents/Projects/invoice/hooks/pre-commit:14, /Users/dave/Documents/Projects/invoice/hooks/pre-commit:14]

Failure scenario

If `hooks/pii-patterns.txt` is ever accidentally deleted, renamed, mis-merged, or excluded by a sparse-checkout, the hook prints a warning to stderr and does `exit 0`, allowing the commit through with zero PII scanning. Many git front ends (GUI clients, some CI wrappers, `git commit` invoked with output redirected) do not surface hook stderr prominently, so this silent full-bypass of the 'No PII in the project' guard could go unnoticed for an arbitrary number of commits before anyone realizes the pattern file is gone.

hooks/pre-commit:40 CONFIRMED

grep -niE -f <(pattern_list) errors are swallowed by `|| true`, silently disabling the PII check

Failure scenario

hooks/pii-patterns.txt is hand-edited free-form regex (confirmed by reading the file); if a future entry has an unescaped/unbalanced metacharacter (e.g. a phone-number pattern with a stray '('), grep -E exits 2 with a stderr syntax error and empty stdout. The `|| true` fallback converts that failure into an empty `hits` string identical to 'no PII found', so the commit is silently ALLOWED through with the guard effectively disabled and zero indication to the committer that pattern matching never ran. Verified locally: a malformed pattern file makes `grep -niE -f bad.txt` exit 2, and wrapping it in `|| true` yields exit 0 with no output.

hooks/pre-commit:35 CONFIRMED

Empty pattern_list after comment/blank stripping exits 0 with no warning, unlike the missing-file case

Failure scenario

If hooks/pii-patterns.txt exists but every effective line is stripped (all comments/blank, e.g. from a bad merge or accidental truncation), pattern_list is empty and the hook exits 0 silently (lines 36-38). This is inconsistent with the missing-file branch (lines 14-17) which prints a `[pre-commit] WARNING ... skipping PII guard` to stderr. A committer has no way to know the PII guard is a no-op in this state, so real PII in the diff is committed without any indication the safety net was inert.

hooks/pre-commit:28 CONFIRMED

`grep -E '^\+[^+]'` only inspects textual diff hunks, so PII embedded in a binary file addition never appears as a `+`-prefixed line and is never scanned.

Failure scenario

Verified: `git diff --cached -U0` for a newly-added binary file (e.g. a screenshot, exported PDF, or .xlsx containing a client's name/SSN) prints only "Binary files /dev/null and b/<path> differ" — no content lines at all. `added_lines` therefore stays effectively empty for that file's content, `hits` never matches, and the commit is silently allowed (exit 0) with zero indication that the file's contents were never checked, defeating the 'No PII in the project' guarantee for any non-.gitignored binary asset.

hooks/pre-commit:1 CONFIRMED

The hook only runs if the developer has manually run `git config core.hooksPath hooks` in this checkout; nothing in the repo enforces, verifies, or warns about that precondition being unmet.

Failure scenario

core.hooksPath is stored in the local, untracked .git/config, so a fresh `git clone` (new machine, CI runner, or a colleague) starts with git's default hooksPath (.git/hooks, which only has the inert pre-commit.sample). Until someone remembers the manual one-time setup step documented in hooks/README.md, every commit — including ones that add real PII — goes through with zero warning, unlike the 'pattern file missing' case in this same script which at least prints a stderr notice; there is no equivalent notice for 'the hook isn't even installed.'

Every one of these was reproduced, not hypothesized: staging a line starting with a literal + (a phone number) demonstrably slips past the added-lines regex; a malformed pattern file demonstrably makes grep exit 2 and the || true demonstrably swallows that into a silent pass; a binary file addition demonstrably shows only "Binary files ... differ" with zero content scanned. The common thread is fail-open behavior with no visible signal — every one of these seven failure modes results in the commit succeeding exactly as if nothing were wrong, which is the worst possible failure mode for a guard whose entire job is to catch things before they're irreversibly pushed.

Where this leaves us

AMake the hook fail closed, not open

Change every silent-pass branch to a loud failure: missing pattern file → block the commit with an actionable error, not a stderr warning + exit 0. Malformed pattern regex → block, don't swallow via || true. Empty pattern list → block with the same warning tier as the missing-file case. Add a binary-file check that blocks (or requires an explicit allowlist) rather than silently passing. Narrow the hooks/* exclude to just the pattern file. Fix the ^\+[^+] regex to correctly handle content that itself starts with +. Separately, move banking secrets into Bitwarden Secrets Manager per the project's own stated convention, and add a repo-root check (e.g. a Makefile target or CI step) that verifies core.hooksPath is actually configured before assuming the guard is active.

What's lost: a fail-closed hook is more likely to occasionally block a legitimate commit (e.g. on a syntax error in the pattern file) until fixed. What's gained: the guard can no longer silently do nothing — every failure mode becomes visible at commit time instead of discovered after the fact.

BAdd hook self-tests, defer the fail-open rewrite

Given the hook has zero automated regression tests today, add a small bats/shell test suite that pins current (broken) behavior as documented, then fix the highest-risk items first (the +-prefix regex and the || true swallow) while deferring the rest.

What's lost: leaves several fail-open paths live for longer. What's gained: establishes a regression-test safety net so future hook edits can't silently reintroduce the same bypasses.

Recommended action

Take Path A for the pre-commit hook this week; treat the plaintext banking secrets and missing file logging as separate, lower-urgency conventions cleanup.

A PII guard that fails open with no visible signal is functionally equivalent to having no guard, which directly conflicts with the "No Secrets Exposure" / "No PII" hard rule this hook exists to enforce. The fixes here are small and mechanical (regex correction, removing an || true, tightening a pathspec) — there's no architectural tradeoff blocking them the way Cluster A has.

Escalate to: n/a — Dave-decidable. Flag if any already-pushed commit history needs a retroactive PII scan given how long these bypasses may have been live; that's a one-time git log audit, not a design call.
